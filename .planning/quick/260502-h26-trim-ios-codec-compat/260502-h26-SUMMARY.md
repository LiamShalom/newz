# Quick Task 260502-h26 — Re-encode non-H.264 sources in `_sync_trim` (shipped)

## What shipped

`backend/pipeline/stitch.py:_sync_trim` now probes its input video codec via ffprobe before deciding how to write the output:

- **H.264 source** (iPhone Safari MediaRecorder) → existing fast `-c copy` path. ~50-100 ms. iPhone Safari plays.
- **Anything else** (Chromebook / desktop Chrome MediaRecorder produces VP8/VP9 + Opus inside WebM) → libx264 + AAC re-encode with `yuv420p` + `+faststart`. ~1-3 s. iPhone Safari plays.
- **Probe failure** → libx264 fallback. Fail-safe.

Two new helpers extracted for testability:
- `_probe_video_codec(path, headers=None) -> str` — wraps `ffmpeg.probe`, returns `""` on any failure.
- `_pick_trim_output_kwargs(src_video_codec) -> dict` — pure function returning ffmpeg output kwargs based on codec.

## Why

`_sync_trim` produces the per-angle videos visible at `segment.video_urls[i]` in the feed. Before this fix, `-c copy` blindly wrapped whatever codec the source had into an `.mp4` container. The function's own comment at lines 142-148 documented the trade-off as "acceptable for the demo target (iPhone Safari producing H.264 .mp4)."

That assumption broke on 2026-05-02 when a 3-angle Chromebook-recorded montage hit the feed. Chrome on ChromeOS doesn't have an H.264 encoder (licensing) so the per-angle URLs were `mp4`-wrapped VP9. **Mac Safari** decodes that. **iPhone Safari** does not — black video, no sound. Confirmed by direct URL test: same per-angle URL plays in Mac Safari but renders black on iPhone Safari standalone.

The stitched `segment.url` was always iOS-safe because `_sync_stitch` already re-encodes through libx264. Only the per-angle trims were affected.

## Performance notes

- H.264 hot path: ~50-100 ms → ~100-150 ms (one extra ffprobe per trim). Acceptable.
- Non-H.264 path: ~50-100 ms → ~1-3 s (libx264 encode). Trade-off worth it; without it, those clips are silently broken on the primary surface (iOS Safari per CLAUDE.md).
- No effect on `_sync_stitch` — that path is untouched.

## Out of scope (deferred)

- Frontend "if angle URL fails to decode, fall back to segment.url" — would mask future bugs.
- AV1 / HEVC inputs — covered by the libx264 fallback.
- Audio codec normalization beyond AAC — pilot scale doesn't hit anything else.

## Surprises / notes

- The existing comment at `stitch.py:142-148` had already foreseen this exact failure mode and called it "acceptable for the demo target." The pilot expanded the demo target — Chromebooks now post — and the comment stopped being accurate. Updated.
- ffprobe adds a network round-trip when the source is a remote Blob URL. Mitigated: same auth headers as the trim itself, and we're streaming the same URL into ffmpeg immediately after, so the data is hot in any caching layer.
- ffprobe codec names are lowercase canonical (`h264`, `vp9`, `vp8`, `av1`) per libavcodec convention. No `.lower()` needed.
