# Quick Task 260502-h26 — Re-encode non-H.264 sources in `_sync_trim` for iOS Safari

## Problem

`backend/pipeline/stitch.py:136 _sync_trim` does a fast `-c copy` (vcodec=copy, acodec=copy) into an `.mp4` container, regardless of the input codec. The function's own comment at lines 144-148 documents the trade-off:

> *"Output is .mp4 regardless of input extension; if input is webm/VP9 the trim will produce an mp4 container around VP9 which iOS won't play. That's an acceptable trade for the demo target (iPhone Safari producing H.264 .mp4)."*

The "acceptable trade" assumed *every* MediaRecorder source was iPhone Safari (which does produce H.264). It bites in practice when:

- Recordings come from a **Chromebook / desktop Chrome** — MediaRecorder defaults to WebM with VP8/VP9 video and Opus audio (Chrome on ChromeOS lacks an H.264 encoder)
- Trim wraps that WebM stream into an `.mp4` container with `-c copy`
- Result: an `.mp4` file containing VP8/VP9+Opus
- **Mac Safari** (≥ 14) decodes VP9-in-mp4 → plays fine
- **iPhone Safari** does NOT decode VP9-in-mp4 → black screen, no sound

Live confirmation 2026-05-02: a 3-angle Chromebook-recorded montage shows up in the feed on iPhone Safari with title + caption + working angle nav, but the `<video>` element renders black. The same per-angle URL fails in iPhone Safari standalone but plays in Chrome and Mac Safari.

`_sync_stitch` (the multi-source path) already re-encodes through `libx264 yuv420p +faststart`, so the **stitched** segment.url is iOS-safe. Only the **per-angle** trims (`segment.video_urls[i]`) are broken.

## Scope

Backend-only. Single primary file edit. Behavior change: non-H.264 trims gain ~1-3 s of encode latency; H.264 trims (the iPhone Safari hot path) stay on the fast `-c copy` path.

## Tasks

### T1 — Codec-aware branching in `_sync_trim`

**Files:**
- `backend/pipeline/stitch.py` — add `_probe_video_codec` helper; add `_pick_trim_output_kwargs(src_codec)` pure helper; rewrite `_sync_trim` to probe → branch.

**Action:**

1. Add `_probe_video_codec(path: str, headers: dict | None = None) -> str` — wraps `ffmpeg.probe(...)` selecting the first video stream, returns `codec_name`. Returns `""` on any probe failure (caller treats `""` as unknown → re-encodes).
2. Add `_pick_trim_output_kwargs(src_codec: str) -> dict` — returns ffmpeg output kwargs based on codec. H.264 → `{vcodec: copy, acodec: copy, format: mp4, movflags: +faststart, avoid_negative_ts: make_zero}`. Anything else → `{vcodec: libx264, preset: ultrafast, crf: 28, pix_fmt: yuv420p, acodec: aac, format: mp4, movflags: +faststart, avoid_negative_ts: make_zero}`. Pure function — easy to unit-test.
3. In `_sync_trim`: call `_probe_video_codec(ref["path"], headers_dict)` before constructing the ffmpeg command, then use `_pick_trim_output_kwargs(codec)`. Log the chosen path (`trim ok output=... codec=... reencoded=true|false`).
4. Update the lines 142-148 docstring comment block to note the codec-aware behavior.

**Edge cases:**
- Probe raises (corrupt file / 404 / network error on Blob URL) → caught, returns `""` → `_pick_trim_output_kwargs("")` falls through to libx264 path → safe default. We re-encode rather than fail.
- File has no video streams → `streams[0]` IndexError caught → returns `""` → re-encode path. ffmpeg will then fail loudly, surfacing the bug.
- File is already H.264 in non-mp4 container (e.g. H.264 in webm) → probe returns `"h264"` → fast `-c copy` works because the codec is iOS-compatible, only the container changes.

## Out of scope

- Frontend fallback "if angle URL fails to load, swap to segment.url" — would mask the bug rather than fix it.
- Force iPhone Safari MIME ladder for desktop browsers — Chrome on ChromeOS literally cannot encode H.264 (no licensed encoder), so a frontend-side fix can't help.
- AV1 / HEVC handling — pilot scale doesn't see these from MediaRecorder; libx264 fallback covers them anyway.
- Audio drop on non-H.264 path — keeping audio (re-encoded to AAC) is the right call. Stitch drops audio on purpose; trims preserve it for single-angle playback context.
- ffmpeg-version-conditional probe paths — `ffmpeg.probe` is stable across the version we target.

## Security notes

- `ref["path"]` is constructed by backend pipeline code (not user input); both `ffmpeg.probe` and `ffmpeg.input` invoke ffprobe / ffmpeg via `subprocess.run` with argument-list (not shell), so no command injection surface even if `path` contained shell metacharacters.
- The `headers` string forwarded to `-headers` is built from internal blob auth dict; same subprocess-list invocation path. CRLF terminators per ffmpeg's HTTP protocol convention (already in use at line 164).
- ffprobe on remote URLs adds one HTTP HEAD/GET round-trip per trim. For Blob-hosted clips this is a small additional load on the proxy; mitigated by the fact that we're already streaming the same URL into the trim command immediately after.

## Performance impact

- H.264 hot path (iPhone Safari source): `_sync_trim` time goes from ~50-100 ms to ~100-150 ms (one extra ffprobe). Acceptable.
- Non-H.264 path (Chromebook / desktop Chrome source): ~50 ms probe + 1-3 s libx264 encode. The encoding cost is the price of iOS compatibility — without it, those clips are unplayable on the primary surface (iOS Safari, per CLAUDE.md).
- No latency regression on `_sync_stitch` — that path is untouched.

## must_haves

- `_sync_trim` no longer produces VP8/VP9-in-mp4 output for non-H.264 inputs.
- H.264 inputs continue to use the fast `-c copy` path (no regression for iPhone Safari recordings).
- Probe failure falls through to the safe (libx264) default — bug-induced black videos get re-encoded, not crashed.
- New unit tests cover the three branches; existing `test_stitch_perf.py` still passes.
- Comment block at lines 142-148 updated to reflect the new behavior — no stale "acceptable trade" claim left in the codebase.
