# Quick Task 260502-w52: Summary

## What changed

Feed and comment-popup videos now auto-unmute on the first user gesture (TikTok pattern). Initial mute state stays `true` so iOS Safari still autoplays the feed; the global bus flips to `false` the moment the user taps, touches, or presses a key — typically before they consciously parse the first card.

## Files

- `frontend/src/muteBus.ts` — added `armAutoUnmute()` (one-shot capture-phase `pointerdown` / `touchstart` / `keydown` listener), `disarmAutoUnmute()` (idempotent cleanup), and the `[data-mute-control]` opt-out check. `setMuted()` now disarms so an explicit user preference is never overridden.
- `frontend/src/main.tsx` — calls `armAutoUnmute()` once before `createRoot`.
- `frontend/src/components/SegmentCard.tsx` — feed mute button now carries `data-mute-control`.
- `frontend/src/components/CommentPopup.tsx` — popup mute button now carries `data-mute-control`.

## Why not just `let muted = false`?

iOS Safari unconditionally blocks autoplay of unmuted media. Defaulting the bus to `false` would mean every feed video sits paused on load, regressing the core feed UX on the primary surface (per CLAUDE.md hard constraint and the existing comment in `muteBus.ts:3-6`). Auto-unmute on first gesture is the TikTok/Instagram Reels pattern and is what "audio on by default" actually means in product terms.

## The race that `[data-mute-control]` solves

Without it, the user's first gesture being on the mute button would cause:

1. capture-phase `pointerdown` fires → auto-unmute → `muted=false`
2. bubble-phase `click` fires → `toggleMute` reads stale `muted=true` from closure → `setMuted(true)` → muted again

Net result: tap-to-unmute appears to no-op. Tagging the button lets the auto-unmute listener bow out and the click handler do its job.
